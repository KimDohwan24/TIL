통합 테스트 3분 30초를 1분으로 줄인 과정

Spring 컨텍스트 캐시, 공유 Testcontainers, 데이터 정리 한 곳으로

2026년 11월 15일 7분 읽기

#Spring Boot#Testcontainers#JUnit#Test#Performance

들어가며

낚시 게임 서버의 통합 테스트는 Testcontainers로 MySQL과 Redis를 띄워서 돈다. 기능이 늘면서 전체 테스트가 3분 30초까지 늘었다. 동시성 테스트를 반복해서 돌려야 하는데 한 번에 3분 반이면 피드백이 너무 느리다.

측정

같은 PC에서 .\gradlew test --rerun-tasks로 정리 전후를 쟀다.

  정리 전 정리 후
전체 시간 3분 30초 1분 3초
테스트 수 269 272 (가드 2, 락 순서 1 추가)
MySQL·Redis 컨테이너 기동 9회 1회
Spring 컨텍스트 생성 9회 2회

컨텍스트 2회는 공용 1개와, @MockitoSpyBean을 쓰는 재시도 테스트 1개다. 이 테스트는 빈 구성이 달라서 따로 만들어진다.

원인

테스트 클래스마다 @Import와 설정이 조금씩 달랐다. Spring의 테스트 컨텍스트 캐시는 설정이 완전히 같을 때만 컨텍스트를 재사용한다. 그래서 클래스마다 컨텍스트를 새로 만들었고, 컨테이너도 클래스마다 새로 기동했다.

해결

1. 공용 @IntegrationTest로 설정을 하나로

@SpringBootTest + MockMvc + 공용 @Import를 @IntegrationTest 하나로 묶었다. 클래스마다 달랐던 @Import(Config, 내부 컨트롤러, 한 테스트가 쓰던 자체 MutableClock)는 BiteTestSupport.Config와 TestEndpoints로 모았다. 설정이 같으니 Spring이 컨텍스트를 캐시해서 재사용한다. 시간을 더 많이 줄인 쪽은 이쪽이다.

2. 컨테이너는 JVM에서 한 번만, 그리고 destroyMethod = ""

컨테이너를 static 필드로 한 번만 띄우고 @Bean으로 돌려준다. 여기에 함정이 있었다. 컨테이너는 AutoCloseable이라서 Spring이 close()를 종료 메서드로 추론해 컨텍스트가 닫힐 때 부른다. 컨텍스트가 둘 이상이면 하나가 닫힐 때 공유 컨테이너가 멈춘다. 그래서 @Bean(destroyMethod = "")로 추론을 끈다. @ServiceConnection은 그대로 쓰고, 컨테이너 정리는 Testcontainers의 Ryuk에 맡긴다.

3. 데이터 정리는 TestDataCleaner 한 곳에서

컨텍스트와 DB를 공유하면 테스트끼리 데이터가 섞이지 않게 해야 한다.

  • @BeforeEach에서 cleaner.clean() 한 줄. FK 자식 → 부모 순서(USER_DATA_TABLES)는 이 클래스에서만 관리한다.
  • fish_records는 마스터 행이라 지우지 않고, 사용자 칸만 NULL로 되돌린다(users 삭제 전에).
  • @AfterEach 정리는 없앴다. 앞 테스트의 데이터는 다음 @BeforeEach가 지우고, 실패한 테스트의 데이터는 디버깅용으로 남는다.

4. 정리 목록을 빠뜨리지 않게 하는 가드 테스트

새 테이블이 생겼는데 클리너를 안 고치면 테스트끼리 오염된다. TestDataCleanerGuardTest가 information_schema의 테이블 목록과 (정리 목록 + 유지 목록)이 같은지 비교한다. V9 마이그레이션처럼 테이블이 늘었는데 클리너를 놓치면 이 테스트가 깨진다.

버린 대안

  • @DirtiesContext: 컨텍스트를 매번 버리니 오히려 느리다.
  • 클래스별 컨테이너: 느리고, 격리로 얻는 이득이 없다(어차피 BeforeEach에서 지운다).

같이 한 일: 동시성 테스트 빈칸 채우기

정리하면서 동시성 테스트 현황도 표로 확인했다. 최초 발견, 강화 중복 차감, 수조 중복 수확, 결과 중복 제출은 이미 있었다. 결과 중복 제출에는 20개 동시 제출이 끝난 뒤 도감 1행, 마릿수 1, 최초·최대 기록 보유자까지 확인하는 검증을 더했다. 또 락 순서 반복 테스트(15라운드, 5초)를 새로 만들었고, 이 테스트가 판매의 데드락을 찾았다. 그 이야기는 같은 날 올린 데드락 글(TIL 38)에 따로 적었다.

배운 점

  • Spring 테스트가 느릴 때 먼저 볼 것은 컨텍스트가 몇 번 만들어지는가다. 설정이 한 글자만 달라도 캐시가 갈린다.
  • 공유 자원을 쓰면 정리 책임을 한 곳에 모으고, 빠뜨리면 실패하는 가드를 둬야 시간이 지나도 안 깨진다.
  • AutoCloseable 빈은 Spring이 close()를 자동으로 부른다는 점을 잊기 쉽다. 공유 자원이면 destroyMethod = ""를 확인한다.
  • 줄이기 전과 후를 같은 조건에서 숫자로 남겨 두면, 나중에 다시 느려졌을 때 비교할 기준이 생긴다.
