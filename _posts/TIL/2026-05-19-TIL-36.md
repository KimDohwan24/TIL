## 개요

AI 뉴스 기반 주식 추천 서비스(StockAI)에서 **조회 속도 저하** 문제를 분석하고, BE(Spring Boot) + FE(Next.js) 전체 스택에 걸쳐 13개 개선 항목과 2개 추가 고려 항목을 정리했다. 순차적 병목 → 병렬화, 2왕복 → 1왕복, 중복 요청 → 캐시 재사용 등의 원칙으로 접근했다.

본문의 시간과 개선율은 구조를 설명하기 위한 예시다. 실제 효과는 캐시 적중률, 외부 API 제한, 동시 요청 수, p95 응답 시간처럼 서비스 환경에서 측정한 지표로 검증해야 한다.

## 1. 국내 주식 배치 가격 조회: 순차 → 병렬

### Before
```
StockPriceBatchService.processChunk()
├─ stockCode[0]: cache miss → KIS API → 125ms
├─ stockCode[1]: cache miss → KIS API → 125ms
├─ stockCode[2]: cache miss → KIS API → 125ms
├─ ... (50개 순차 대기)
└─ stockCode[49]: cache miss → KIS API → 125ms
총 소요: ~6.25초
```

- `Semaphore(10)`, `RateLimiter(8.0/sec)`로 동시성 제어는 있으나 for문 안에서 순차 `acquire()` 후 동기 호출
- 해외 주식(`OverseasStockPriceBatchService`)은 이미 `@Async` + `CompletableFuture` 병렬 패턴인데 국내만 누락

### After
```
StockPriceBatchService.processChunk()
├─ 1차: 캐시 조회 (cache hit 즉시 반환)
└─ 2차: cache miss 항목만 CompletableFuture.allOf() 병렬 dispatch
    ├─ Future[0]: @Async → KIS API
    ├─ Future[1]: @Async → KIS API
    ├─ ... (Semaphore=10, 최대 10개 동시)
    └─ Future[49]: @Async → KIS API
처리 완료 시간: RateLimiter가 초당 8건이면 약 6.25초
```

### 핵심 인사이트
- **동시성 제어 도구(Semaphore, RateLimiter)와 호출 방식(동기/비동기)은 독립적**이다. 제한 도구만 추가한다고 병렬 처리되지는 않으며, 작업을 병렬로 제출하는 구조가 필요하다.
- RateLimiter가 초당 8건을 허용하면 50건 처리에는 이론적으로 **최소 50÷8 ≈ 6.25초**가 필요하다. Semaphore 값을 높여도 외부 API의 TPS 제한을 넘을 수는 없다.
- `@Async`는 작업을 executor에 위임하는 방식이지, I/O 자체를 논블로킹으로 바꾸지는 않는다. KIS 클라이언트가 동기 I/O라면 워커 스레드는 대기한다. 또한 `allOf().get()`을 호출하면 그 호출자는 결과가 끝날 때까지 기다린다. 요청 스레드를 빨리 반환하려면 상위 계층까지 `CompletableFuture` 또는 reactive type을 전파해야 한다.

### 효과

| 지표 | Before | After |
|------|--------|-------|
| 50종목 배치 완료 시간 | ~6.25초 | RateLimiter 한도가 같으면 약 ~6.25초 |
| KIS API 호출 방식 | 순차 동기 호출 | 병렬 작업 위임 (워커 스레드의 I/O 대기는 가능) |
| 호출 스레드 점유 시간 | ~6.25초 | `get()`으로 대기하면 동일, Future를 상위로 반환하면 조기 해제 가능 |
| 타임아웃 처리 | 없음 | `allOf().get(20s)` + cancel |

## 2. OAuth WebClient: 매번 생성 → 싱글톤 재사용

### Before
```java
private WebClient getOAuthClient() {
    return WebClient.builder()
            .baseUrl(kisConfig.getOauthUrl())
            .build();  // 매 호출 시 새 인스턴스
}
```

- 매 호출마다 WebClient 구성 객체를 새로 만든다.
- 기본 커넥션 풀과 리소스의 공유 여부는 connector 설정과 Reactor Netty 버전에 따라 다르다. `build()`마다 새 ConnectionProvider나 TCP 연결이 반드시 만들어진다고 단정할 수는 없다.
- 토큰 발급 경로에는 재사용 여부뿐 아니라 연결·응답 타임아웃과 오류 처리가 필요하다.

### After
```java
// WebClientConfig.java
@Bean("kisOAuthWebClient")
public WebClient kisOAuthWebClient(KisConfig kisConfig) {
    HttpClient httpClient = HttpClient.create()
            .option(ChannelOption.CONNECT_TIMEOUT_MILLIS, 5000)
            .responseTimeout(Duration.ofSeconds(5));
    return WebClient.builder()
            .baseUrl(kisConfig.getOauthUrl())
            .clientConnector(new ReactorClientHttpConnector(httpClient))
            .build();
}
```

### 핵심 인사이트
- WebClient는 immutable하게 재사용할 수 있다. 다만 기본 Reactor Netty 리소스는 전역으로 공유될 수 있으므로, 매 `build()`가 곧바로 메모리 누수를 만든다고 보기는 어렵다.
- Spring Bean으로 재사용하면 base URL, 타임아웃, 관측 설정을 한 곳에서 일관되게 관리할 수 있다.
- 커스텀 `ConnectionProvider`를 사용한다면 이름, 최대 연결 수, idle/lifetime, 종료 시점까지 명시적으로 관리한다. 기본값은 사용하는 라이브러리 버전과 런타임 설정으로 확인한다.

### 효과

| 지표 | Before | After |
|------|--------|-------|
| 클라이언트 구성 | 매 호출마다 구성 | Bean으로 재사용 |
| 커넥션 재사용 | connector·리소스 설정에 따라 다름 | 명시한 ConnectionProvider 정책으로 제어 가능 |
| stale connection 대응 | 기본값과 서버 timeout에 의존 | idle/lifetime·eviction을 서비스 조건에 맞게 설정 |
| 타임아웃 보장 | 없음 | connect 5s, response 5s |

## 3. WebClient 커넥션 풀 설정

### Before
```
Reactor Netty 기본 ConnectionProvider:
- 최대 연결 수, pending queue, idle/lifetime 기본값은 라이브러리 버전과 설정에 따라 달라진다.
- `HttpClient.create()`는 전역 리소스를 사용할 수 있다.
- 실제 값은 사용하는 Reactor Netty 버전의 문서와 런타임 설정으로 확인한다.
```

- 기본 또는 전역 풀의 값이 현재 트래픽과 외부 API 정책에 맞는지 확인하지 않은 상태다.
- 서버의 idle timeout보다 오래 남은 연결은 stale connection 오류를 만들 수 있으므로, 대상 서버 정책과 함께 idle/lifetime 값을 검토해야 한다.

### After
```java
ConnectionProvider provider = ConnectionProvider.builder("kis-pool")
    .maxConnections(100)
    .pendingAcquireMaxCount(500)
    .pendingAcquireTimeout(Duration.ofSeconds(10))
    .maxIdleTime(Duration.ofSeconds(30))
    .maxLifeTime(Duration.ofSeconds(60))
    .evictInBackground(Duration.ofSeconds(30))
    .build();
```

### 핵심 인사이트
- **maxIdleTime과 maxLifeTime의 차이** — idleTime은 마지막 사용 후 경과 시간, lifeTime은 커넥션 생성 후 경과 시간이다. 대상 서버 timeout에 맞춰 둘을 함께 검토한다.
- `evictInBackground`는 별도 주기로 유휴·만료 연결을 정리한다. 설정하지 않으면 정리가 다음 acquire 시점까지 지연될 수 있다.
- 풀 크기는 외부 API의 허용 TPS만으로 정할 수 없다. 요청 지연 시간, 동시 요청 수, 대기열, 애플리케이션 리소스를 함께 측정해야 하며, 100은 검증이 필요한 예시 값이다.

### 효과

| 지표 | Before | After |
|------|--------|-------|
| maxConnections | 기본·전역 설정에 따라 다름 | 100 예시값, 부하 테스트로 확정 |
| idle 커넥션 정리 | 기본값 확인 필요 | 30초 예시값 |
| stale connection 대응 | 서버 timeout과 기본값에 의존 | lifeTime·eviction을 명시해 제어 |
| 메모리 사용 | 설정에 따라 달라짐 | 풀 크기와 대기열을 함께 관찰 |

## 4. 카탈로그 + 가격 통합: 2왕복 → 1왕복

### Before
```
FE (Server Component)
  ├─ 1st: GET /api/stocks?page=0 → 종목 목록 [{stockCode, name, sector...}]
  │         응답에 가격 없음 (또는 캐시에 없으면 withoutPrice)
  └─ 2nd: POST /api/stocks/prices → {005930: {price:...}, 000660: {price:...}}
            ↑ 1st 응답의 stockCode 목록이 필요 → 반드시 순차

왕복: 2회 (waterfall)
```

- BE에 이미 `StockCatalogWithPriceResponse` DTO와 `enrichWithPrice()` 메서드가 존재
- 다만 **캐시에 없는 가격은 `withoutPrice`로 반환** → FE가 별도 batch 호출 필수

### After
```
FE (Server Component)
  └─ 1st: GET /api/stocks?page=0 → {stockCode, name, sector, price, changeRate...}
           enrichWithPrice()에서 캐시 miss 시 StockPriceService로 실시간 조회
           (조회 결과는 @Cacheable에 의해 캐시에도 저장됨)

왕복: 1회
```

### 핵심 인사이트
- **Backend-Driven Enrichment 원칙** — 클라이언트가 조합해야 할 데이터는 서버에서 미리 합쳐서 반환하는 것이 네트워크 왕복을 줄이는 근본적 해결책
- `enrichWithPrice()`에서 "캐시에 없으면 빈 값 반환"은 **안전하지만 비효율적** — 실시간 조회로 채워도 `@Cacheable`에 의해 후속 요청은 캐시 hit가 됨
- 다수의 cache miss가 한꺼번에 발생할 수 있으므로 **배치 병렬화 선행 필수**

### 효과

| 지표 | Before | After |
|------|--------|-------|
| SSR 시 HTTP 왕복 | 2회 (waterfall) | 1회 |
| FE→BE 요청 수 | 2 | 1 |
| TTFB (캐시 hit 시) | ~200ms | ~100ms |
| TTFB (캐시 miss 시) | 외부 API 호출 뒤 별도 가격 요청 | 왕복은 1회로 줄지만, 실제 시간은 miss 수·TPS·지연 시간 측정 필요 |

## 5. HikariCP 커넥션 풀 튜닝

### Before
```
Spring Boot 기본 HikariCP:
- maximumPoolSize: 10
- minimumIdle: 10
- connectionTimeout: 30000ms (30초)
- leakDetectionThreshold: 0 (비활성)
```

- 10개 풀로 고부하 시 커넥션 대기 발생 가능
- 30초 타임아웃은 너무 김 → 장애 시 장시간 응답 지연
- 커넥션 누수 감지 없음

### After
```yaml
spring.datasource.hikari:
  maximum-pool-size: 20
  minimum-idle: 5
  idle-timeout: 300000       # 5분
  max-lifetime: 600000       # 10분
  connection-timeout: 5000   # 5초
  leak-detection-threshold: 10000  # 10초
```

### 핵심 인사이트
- **maximumPoolSize는 "동시 연결 수"가 아니라 "풀의 최대 크기"** — 10개가 다 사용 중이면 11번째 요청은 대기. 서비스의 동시 DB 쿼리 수(동시 가격 조회 + 카탈로그 + 인증 등)를 기준으로 설정해야 함
- `connection-timeout=5000`은 "5초 내 커넥션 획득 실패 시 예외" → 30초 동안 스레드가 블록되는 것 방지
- `leak-detection-threshold=10000`은 커넥션을 10초 이상 반납하지 않으면 WARN 로그를 남겨 누수 조사에 도움을 준다. 운영 환경에서는 정상적인 장기 쿼리에도 경고가 쌓일 수 있으므로 조사 기간에 한시적으로 사용하는 방안도 검토한다.
- **`max-lifetime=10분`은 MySQL `wait_timeout`(기본 28800초=8시간)보다 짧게 설정하는 원칙에는 맞으나, 지나치게 공격적일 수 있다.** 풀 커넥션이 자주 교체되면 불필요한 TCP 재연결이 생긴다. MySQL의 `wait_timeout`과 `interactive_timeout`을 확인한 뒤 그보다 여유를 두고 짧게 설정하고, 부하 테스트로 검증한다.

### 효과

| 지표 | Before | After |
|------|--------|-------|
| 최대 동시 DB 커넥션 | 10 | 20 |
| 장애 시 응답 지연 | 최대 30초 블록 | 5초 타임아웃 |
| 커넥션 누수 감지 | 없음 | 10초 경고 |
| idle 최소 유지 | 10 (불필요한 유지) | 5 |

## 6. Balance/Summary 중복 호출 통합

### Before
```
GET /api/account/balance       → kisApiClient.getBalance() → output1
GET /api/account/balance/summary → kisApiClient.getBalance() → output2
                                                          ↑ 같은 KIS API 2회 호출
```

- 클라이언트가 두 API를 연속 호출하면 동일한 KIS API 요청이 2번 발생
- KIS API는 초당 호출 제한이 있어 중복 호출이 제한 소모

### After
```
getBalanceFull() → kisApiClient.getBalance() 1회 호출
  ├─ getBalance():      캐시된 응답에서 output1 추출
  └─ getBalanceSummary(): 캐시된 응답에서 output2 추출
```

### 핵심 인사이트
- **같은 외부 API를 여러 서비스 메서드에서 호출할 때 캐시 또는 통합이 필요** — 응답의 다른 부분(output1 vs output2)만 필요하더라도, 요청 자체는 동일하므로 1회만 호출
- KIS API의 `getBalance()`는 무거운 호출 (잔고 전체 조회). TTL 10초 캐시면 충분 (실시간성 요구 낮음)

### 효과

| 지표 | Before | After |
|------|--------|-------|
| KIS API 호출 | 2회/요청 | 1회/요청 |
| 초당 호출 제한 소모 | 2 | 1 |
| 응답 시간 (2번째) | ~300ms | 캐시 hit <5ms |

## 7. DB 인덱스: sector 단일 컬럼

### Before
```sql
-- 복합 인덱스만 존재
CREATE INDEX idx_stocks_market_type_sector ON stocks (market_type, sector);

-- findBySector() 쿼리:
SELECT * FROM stocks WHERE sector = '반도체'
-- → 선행 컬럼(market_type) 조건이 없어 이 복합 인덱스를 효율적으로 쓰기 어렵다.
--    실제 계획은 데이터 분포와 DB 옵티마이저에 따라 달라지므로 EXPLAIN ANALYZE로 확인한다.
```

### After
```sql
CREATE INDEX idx_stocks_sector ON stocks (sector);
```

### 핵심 인사이트
- **복합 인덱스의 최좌선 원칙(Leftmost Prefix Rule)** — 일반적으로 `(A, B)` 인덱스는 `A` 조건이 있을 때 가장 잘 활용된다. `WHERE B=?`만으로는 같은 효율을 기대하기 어렵다.
- 단일 컬럼 인덱스는 후보가 될 수 있지만, 선택도가 낮거나 테이블이 작으면 옵티마이저가 Seq Scan을 선택할 수 있다. 추가 전후에 `EXPLAIN ANALYZE`와 실제 지연 시간을 비교한다.

### 효과

| 지표 | Before | After |
|------|--------|-------|
| `findBySector()` 실행 계획 | `EXPLAIN ANALYZE`로 현재 계획 확인 | 새 인덱스를 사용할 수 있으나 데이터 분포에 따라 달라짐 |
| 조회 시간 | 현재 환경에서 측정 | 같은 데이터·부하 조건에서 전후 비교 |

## 8. Circuit Breaker Fallback: 장애 전파 → Graceful Degradation

### Before
```java
private StockPriceResponse getStockPriceFallback(Exception e) {
    throw new RuntimeException("Circuit open");  // 호출부로 예외 전파
}
```

- CB가 열리면 모든 가격 조회가 500 에러
- 프론트엔드는 에러 표시 또는 빈 값

### After
```java
private final ConcurrentMap<String, StockPriceResponse> lastGoodPrices =
        new ConcurrentHashMap<>();

private StockPriceResponse getStockPriceFallback(String stockCode, Exception e) {
    StockPriceResponse lastGood = lastGoodPrices.get(stockCode);
    if (lastGood != null) {
        // 저장된 DTO를 직접 변경하지 않고, stale 표시가 있는 복사본을 반환하는 예시
        return copyWithError(lastGood, "CIRCUIT_OPEN_STALE");
    }
    return errorResponse("CIRCUIT_OPEN");
}
```

### 핵심 인사이트
- **Circuit Breaker의 목적은 "장애 격리"** — fallback에서 예외를 throw하면 격리가 아니라 형태만 바뀐 장애 전파
- 호출부가 이미 `error` 필드를 체크하는 구조(`if (price.getError() == null)`)라면, fallback이 에러 DTO를 반환하는 것이 자연스러운 흐름
- 사용자는 "일시적 오류" 메시지를 보는 대신 "가격 정보 없음"으로 부드럽게 저하
- **Stale Data 전략** — 마지막 정상 응답은 반드시 종목 코드별로 저장하고 thread-safe하게 다뤄야 한다. 전역 `lastGoodResponse` 하나를 쓰면 다른 종목의 가격을 잘못 반환할 수 있다. 데이터 시각과 stale 상태를 함께 내려 FE에서 표시한다.

### 효과

| 지표 | Before | After |
|------|--------|-------|
| CB open 시 FE 응답 | 500 에러 (화면 깨짐) | 오류 DTO 또는 동일 종목의 stale data + 시각·오류 표시 |
| 연쇄 장애 | 가능 | 차단 |
| UX | 전체 페이지 에러 | 개별 종목 가격 숨김 또는 마지막 가격 표시 |

## 9. FE 카탈로그 Waterfall 제거

### Before
```
Server Component:
  const catalog = await getStocks(...)      // ~200ms
  const prices = await getBatchPrices(codes) // ~6s (전체 cache miss 시)
  // 총: ~6.2초 (순차)
```

### After
```
Server Component:
  const catalog = await getStocks(...)  // 이미 가격 포함 (~200ms + 실시간 조회)
  const prices = catalog에서 추출       // 0ms (추출만)
  // 총 시간: 캐시 적중률, 외부 API 지연, RateLimiter 조건에 따라 측정
```

### 핵심 인사이트
- **Server Component에서의 waterfall은 TTFB에 직접 영향** — CSR에서는 병렬 useSWR이 가능하지만, SSR에서는 `await`의 순차 실행이 불가피
- 해결책은 "FE에서 병렬화"가 아니라 **"BE에서 합쳐서 보내기"** — 근원적 해결
- 후속 페이지(infinite scroll)의 delta 조회는 유지: SSR은 첫 페이지만 담당

### 효과

| 지표 | Before | After |
|------|--------|-------|
| SSR HTTP 왕복 | 2 | 1 |
| TTFB (cache hit) | ~400ms | ~200ms |
| TTFB (cache miss) | 목록·가격을 순차 요청 | 왕복은 1회지만 외부 API 지연과 miss 수에 따라 측정 필요 |
| FE 복잡도 | 서버에서 batch 호출 필요 | initialData에서 바로 추출 |

## 10. TradePanel raw fetch → SWR 전환

### Before
```tsx
useEffect(() => {
  getHoldings().then(setUserHolding).catch(...);
}, [isAuthenticated, stockCode]);
// 페이지 이동 시마다 재요청, dedup 없음
```

### After
```tsx
const { data: holdings } = useSWR(
  isAuthenticated ? 'user-holdings' : null,
  getHoldings,
  { dedupingInterval: 5000 }
);
// 동일 key면 dedup, Dashboard와 캐시 공유
```

### 핵심 인사이트
- **raw fetch + useEffect는 SWR의 dedup, 캐시, 재검증 이점을 모두 포기하는 것** — 동일한 API를 다른 컴포넌트에서 다른 전략으로 호출하면 중복 요청 발생
- SWR key를 통일하면 여러 컴포넌트가 같은 캐시를 공유 → 네트워크 요청 1회로 N개 컴포넌트 업데이트

### 효과

| 지표 | Before | After |
|------|--------|-------|
| 페이지 이동 시 holdings 요청 | 매번 | dedup (설정한 5초 내 중복 제거) |
| Dashboard ↔ 상세 페이지 캐시 | 공유 안됨 | 동일 key로 공유 |
| 주문 후 갱신 | 수동 fetch | `mutate('user-holdings')` |

## 11. 렌더 중 dispatch 제거: useEffect 또는 useMemo

### Before
```tsx
if (deltaPrices) {
  dispatch({ type: 'merge', prices: deltaPrices });
}
// 렌더 함수 본문 내에서 state 변경 → React가 두 번 렌더링함
```

- SWR이 `deltaPrices`를 갱신 → 리렌더 1회 + dispatch로 reducer 상태 변경 → 리렌더 1회 = **동일 데이터에 2회 렌더**

### After
```tsx
useEffect(() => {
  if (deltaPrices) dispatch({ type: 'merge', prices: deltaPrices });
}, [deltaPrices]);
```

### 핵심 인사이트
- **렌더 단계에서 state를 변경하면 안 된다.** `useEffect`는 업데이트를 commit 이후로 옮겨 경고와 무한 렌더 위험을 피하지만, effect의 dispatch 때문에 추가 렌더가 한 번 더 발생할 수 있다.
- `accumulatedPrices`가 다른 상태에서 계산 가능한 값이라면 `useMemo`로 합성해 reducer와 dispatch 자체를 없앨 수 있다:

```tsx
const accumulatedPrices = useMemo(() => {
  const merged = { ...initialPrices };
  if (deltaPrices) Object.assign(merged, deltaPrices);
  return merged;
}, [initialPrices, deltaPrices]);
```

이렇게 하면 reducer와 dispatch를 완전히 제거할 수 있으며, 리렌더도 SWR 갱신 시 1회만 발생함

### 효과

| 지표 | Before | After |
|------|--------|-------|
| 렌더 중 state 변경 경고 | 가능 | `useEffect`·`useMemo` 방식에서는 없음 |
| 추가 state 업데이트 | reducer dispatch 필요 | `useEffect`는 추가 렌더 가능, `useMemo`는 파생 값이면 제거 가능 |

## 13. 캔들 데이터 SWR 전환

### Before
```tsx
const [state, dispatch] = useReducer(reducer, initialState);

const fetchCandleData = useCallback(() => {
  dispatch({ type: 'FETCH_START' });
  getDailyCandles({...}).then(d => dispatch({type:'FETCH_CANDLES_SUCCESS', payload: d}));
}, [...]);

useEffect(() => { fetchCandleData(); }, [fetchCandleData]);
```

### After
```tsx
const { data: candles, isLoading: candlesLoading } = useSWR(
  stockCode ? ['daily-candles', stockCode, period, startDate, endDate] : null,
  () => getDailyCandles({stockCode, period, startDate, endDate}),
  { revalidateOnFocus: false }
);

const { data: minuteCandles } = useSWR(
  viewMode === 'minute' && stockCode ? ['minute-candles', stockCode] : null,
  () => getMinuteCandles(stockCode),
  { revalidateOnFocus: false }
);
```

### 핵심 인사이트
- **로딩/에러/데이터 상태 관리는 SWR이 이미 제공** — `useReducer`로 직접 관리하면 코드 중복 + 버그 가능성 증가
- SWR key에 파라미터를 포함하면 파라미터 변경 시 자동 재요청 → `useCallback` 의존성 관리 불필요
- `viewMode === 'minute'` 조건부 key(null이면 fetch 안 함)로 불필요한 API 호출 방지

### 효과

| 지표 | Before | After |
|------|--------|-------|
| 상태 관리 코드 | ~30행 (reducer + action types) | 제거 |
| 캐시/dedup | 없음 | SWR 자동 |
| period 변경 시 재요청 | 수동 useCallback 관리 | key 변경으로 자동 |

| KIS 토큰 발급 경로 | 클라이언트 설정이 분산 | Bean과 풀 정책을 한 곳에서 관리 | **운영 일관성↑** |

| 종목 상세 페이지 이동 | holdings 중복 요청 | SWR dedup | **중복 제거** |
| badge retry 네트워크 비용 | 50종목 재요청 | 1종목 단건 | **98%↓** |

### 핵심 교훈 3가지
1. **서버에서 합쳐서 보내면 클라이언트 waterfall은 사라진다** — FE 최적화보다 BE 응답 구조 개선이 근본적
2. **동시성 제어 ≠ 병렬 처리** — Semaphore와 RateLimiter는 제한일 뿐이다. `@Async`는 작업을 executor에 위임하지만, 동기 I/O와 `get()` 대기는 별도로 고려해야 한다
3. **캐시 전략은 "miss 시 어떻게 채울 것인가"까지 설계해야 한다** — hit만 최적화하면 miss 경로가 새 병목이 됨

## 추가 고려 항목

### 14. Cache Stampede 방지

다수의 cache miss가 동시에 발생하면, 여러 스레드가 동일 키에 대해 외부 API를 중복 호출함.

```java
// @Cacheable만 사용 시: 10개 스레드가 동시에 getStockPrice("005930") 호출 → KIS API 10회
// 해결: @Cacheable + CacheLoader 또는 stampede guard
@Cacheable(value = "stockPrice", key = "#stockCode", sync = true)
public StockPriceResponse getStockPrice(String stockCode) { ... }
```

- Spring의 `sync = true`는 같은 키에 대해 **1개 스레드만 로드**하고 나머지는 대기 → 중복 API 호출 방지
- 대규모 트래픽에서는 분산 락(Redis) 또는 `Caffeine`의 `RefreshAfterWrite`도 고려

### 15. FE Error Boundary 적용

CB fallback이 정상 응답을 반환하더라도, FE 렌더링 중 예외(예: stale data의 null 필드 접근)가 발생하면 전체 페이지가 깨질 수 있음.

```tsx
<ErrorBoundary fallback={<StockCardSkeleton />}>
  <StockCard stock={stock} />
</ErrorBoundary>
```

- 개별 종목 카드 단위로 Error Boundary를 감싸면, 한 종목의 렌더 에러가 전체 목록에 영향을 주지 않음
- Next.js에서는 `error.tsx`로 라우트 세그먼트 수준의 오류를 대응할 수 있다.
