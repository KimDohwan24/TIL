## 들어가며

낚시 게임 서버(Spring Boot + MySQL 8.4)를 만들면서 데드락을 네 번 만났다. 네 번 모두 "가끔 실패하는 테스트"로 시작했다. 한 번 더 돌리면 통과해서 넘어가기 쉬웠지만, 실제 서비스에서는 같은 계정으로 요청이 겹칠 때 그대로 터질 문제였다.

이 글은 각각 어떻게 재현했고, 원인이 무엇이었고, 어떤 방법을 고르고 무엇을 버렸는지 정리한 기록이다.

| 번호 | 상황 | 원인 한 줄 | 결과 |
| --- | --- | --- | --- |
| 1 | 같은 닉네임 동시 가입 (#29, PR #36) | 유니크 인덱스 S 락끼리 X 락을 기다림 | 50라운드 중 2~3번 나던 500 → 0번 |
| 2 | 구역 개방 동시 요청 (PR #38) | INSERT를 먼저 해서 S 락 경쟁 | 락 충돌 168건 → 0건 |
| 3 | 미끼 구매 ↔ 던지기 (PR #40) | 두 흐름의 락 순서가 반대 | `users`를 먼저 잠그도록 통일 |
| 4 | 판매 (PR #42) | 판매만 `catches` → `users` 순서 | 락 실패 9건 → 0건 |

## 1. 동시 가입에서 가끔 나던 500

### 문제

같은 닉네임으로 20명이 동시에 가입하면 한 명만 성공하고 19명은 `409 NICKNAME_DUPLICATED`를 받아야 한다. 이 테스트가 전체 테스트 첫 실행에서 한 번 실패했다. 19명 중 16명만 `NICKNAME_DUPLICATED`였고, 로그에 `Deadlock found when trying to get lock`이 3건 있었다. 다시 돌리면 통과했다.

### 재현

"가끔"이라서 한 번 돌려서는 못 잡는다. 임시 테스트를 만들어 같은 닉네임 `register`를 20스레드가 `CountDownLatch`로 동시에 출발하게 하고, 이를 50라운드(라운드마다 `users` 삭제) 반복했다. Testcontainers MySQL 8.4 위에서 돌렸다.

| | 라운드 실패 | 요청 실패(500) | 예외 |
| --- | --- | --- | --- |
| 고치기 전 1회차 | 2 / 50 | 4 / 1000 | `CannotAcquireLockException` |
| 고치기 전 2회차 | 3 / 50 | 7 / 1000 | `CannotAcquireLockException` |
| 고친 뒤 1회차 | 0 / 50 | 0 / 1000 | 없음 (OK 50, NICKNAME_DUPLICATED 950) |
| 고친 뒤 2회차 | 0 / 50 | 0 / 1000 | 없음 (OK 50, NICKNAME_DUPLICATED 950) |

한 라운드가 실패할 확률이 4~6% 정도라서, 회귀 테스트는 한 테스트 안에서 20라운드를 돌리게 했다.

### 원인

`SHOW ENGINE INNODB STATUS`의 `LATEST DETECTED DEADLOCK`을 보면 다음과 같다(발췌).

```text
*** (1) TRANSACTION: 2462  insert into users (...)
*** (1) HOLDS THE LOCK(S):   index uk_users_nickname  lock mode S
*** (1) WAITING FOR:         index uk_users_nickname  lock_mode X insert intention waiting
*** (2) TRANSACTION: 2461  insert into users (...)
*** (2) HOLDS THE LOCK(S):   index uk_users_nickname  lock mode S
*** (2) WAITING FOR:         index uk_users_nickname  lock_mode X insert intention waiting
*** WE ROLL BACK TRANSACTION (2)
```

| 시점 | 트랜잭션 A | 트랜잭션 B |
| --- | --- | --- |
| 1 | 유니크 인덱스 중복 검사: S 락 획득 | 중복 검사: S 락 획득 (S끼리는 호환) |
| 2 | 삽입하려고 X(insert intention) 요청 → B의 S 때문에 대기 | |
| 3 | | X(insert intention) 요청 → A의 S 때문에 대기 |
| 4 | 서로 상대의 S가 풀리길 기다림 = 순환 대기 | InnoDB가 한쪽을 롤백 |

희생된 트랜잭션은 Spring이 `CannotAcquireLockException`으로 바꿔 던진다. 그런데 기존 코드는 `DataIntegrityViolationException`만 `NICKNAME_DUPLICATED`로 바꿨고, 나머지는 `Exception` 핸들러가 500으로 응답했다. 데드락 자체는 InnoDB의 정상 동작이었고, **락 실패를 어떻게 다루느냐**가 버그였다.

### 고른 해결과 버린 대안

| 안 | 장점 | 단점 |
| --- | --- | --- |
| A. 락 예외를 잡아 재조회 → 있으면 `NICKNAME_DUPLICATED` | 코드가 짧다 | 승자가 아직 커밋 전이면 재조회가 빈손이라 판단이 틀린다. 같은 트랜잭션은 이미 롤백 표시라 쓸 수 없다 |
| **B. 트랜잭션 밖에서 재시도 (선택)** | 재시도 때 선행 SELECT가 커밋된 승자를 보고 정확히 `NICKNAME_DUPLICATED`를 낸다 | 루프와 설정이 늘고, 최악 지연이 조금 늘어난다(20ms × 2) |
| C. 락 실패를 공통 409로만 응답 | 가장 단순하다 | 사용자에게 정답은 "이미 사용 중"인데 "다시 시도"가 보인다 |

가입은 짧고 되풀이해도 안전하다(실패한 시도는 롤백되어 흔적이 없다). 그래서 B를 골랐고, C는 안전망으로 같이 뒀다. 재시도를 다 써도 락 실패면 409 `CONFLICT`를 준다.

구현에서 신경 쓴 점은 두 가지다.

- 바깥 `UserService.register`는 트랜잭션이 없고, 시도 한 번은 **별도 빈** `SignupTransaction.attempt`의 `@Transactional`로 감쌌다. 같은 클래스 안에서 `this.attempt()`로 부르면 프록시를 거치지 않아 `@Transactional`이 적용되지 않는다. 또 재시도 루프가 트랜잭션 안에 있으면 롤백 표시된 트랜잭션을 다시 쓰게 된다.
- 재시도는 `spring-retry` 없이 직접 쓴 루프다. 대상 예외가 `PessimisticLockingFailureException` 하나이고, 횟수(`max-attempts=3`)와 대기(`backoff=20ms`)가 설정값이라 의존성을 늘릴 이유가 없었다.

`GlobalExceptionHandler`에는 `PessimisticLockingFailureException` → 409 `CONFLICT`를 추가했다. 응답에는 내부 메시지를 담지 않는다. 덕분에 다른 동시성 API에서 락 실패가 새도 500이 아니라 409가 된다. 다만 실제로 데드락이 재현된 곳은 이때까지 가입뿐이었다.

## 2. 구역 개방: INSERT가 먼저냐, 골드 차감이 먼저냐

### 문제

낚싯대 강화와 골드로 구역을 여는 기능(PR #37)에서, 같은 계정으로 12개 요청을 동시에 보내자 `Deadlock found when trying to get lock`이 났다. API에서는 409 `CONFLICT`로 바뀌어 나가서 결과(골드 1번 차감, 구역 1번 열림)는 맞았다. 하지만 정상적인 패배 응답인 `ZONE_ALREADY_UNLOCKED`가 아니라 일반 충돌로 나가고, 서버 로그에 데드락 경고가 쌓였다. 불필요한 데드락이다.

### 원인

기존 순서는 `user_zones` INSERT → 골드 차감이었다. 같은 `(user_id, zone_id)`를 동시에 INSERT하면 InnoDB는 중복 키를 만난 요청에게 그 인덱스 레코드의 S 락을 걸고 기다리게 한다. 여러 요청이 S 락을 같이 쥔 채 앞 요청이 롤백되면, 모두 X 락으로 올리려다 서로를 기다린다. 1번의 가입 데드락과 같은 종류다.

### 고른 해결과 버린 대안

**골드 차감(`users` 행 UPDATE, X 락)을 먼저** 하도록 순서를 바꿨다. 동시 요청이 `users` 행의 X 락에서 한 줄로 서서 하나씩 들어오므로 INSERT 경쟁 자체가 생기지 않는다. 먼저 들어온 요청이 커밋하면 뒤 요청은 `user_zones`에서 PK 중복을 만나 `ZONE_ALREADY_UNLOCKED`(409)가 된다. 예외로 트랜잭션이 롤백되니 그 요청의 골드 차감도 함께 취소되고, 골드는 한 번만 빠진다.

버린 대안은 INSERT 실패를 재시도하는 방법이다. 락 순서를 맞추면 데드락이 아예 없어서 재시도가 필요 없다.

### 결과

동시 개방 테스트를 20라운드 반복으로 바꾸고, 테스트가 락 충돌을 허용하던 부분을 없앴다(실패 코드는 `ZONE_ALREADY_UNLOCKED`만 허용).

| | 20라운드 중 락 충돌 | 테스트 |
| --- | --- | --- |
| 수정 전 (INSERT 먼저) | 168건 | 실패 |
| 수정 후 (골드 차감 먼저) | 0건 (2회 실행 모두) | 통과 |

## 3. 미끼 구매와 던지기: 서로 반대로 잠그기

### 문제

미끼 구매와 던지기를 같은 계정에서 섞어 돌리는 테스트(`ShopConcurrencyTest`)에서 데드락이 났다.

### 원인

- 미끼 구매: `users`(골드 차감) → `user_baits`
- 던지기: `user_baits`(개수 차감) → `bite_sessions` INSERT. 이때 FK 검사가 `users` 행에 공유 락을 건다.

한쪽은 `users` → `user_baits`, 다른 쪽은 `user_baits` → `users`. 순서가 반대라서 서로를 기다렸다.

### 해결

던지기에서 미끼를 쓰기 전에 `SELECT id FROM users WHERE id=? FOR UPDATE`(`UserService.lockForUpdate`, 전파 속성 `MANDATORY`)로 `users`를 먼저 잠그게 했다. **락 순서를 `users` → `user_baits`로 통일**한 것이다. 이 락은 미끼를 쓸 때만 건다. 테스트에서는 이 흐름이 데드락 없이 돈다.

여기서 "데드락이 나면 재시도하자"가 아니라 "순서를 맞추자"가 기본 방침이 됐다. 순서가 같으면 서로 기다릴 일이 없고, 사용자가 한 번 누른 구매를 서버가 다시 돌리지도 않는다.

## 4. 락 순서를 표로 만들었더니 판매만 거꾸로였다

### 문제

세 번을 겪고 나니 "다음은 어디서 날까"가 걱정이었다. 그래서 모든 흐름이 어떤 순서로 락을 잡는지 코드를 읽어 표로 정리했다.

| 흐름 | 잠그는 순서 (X=쓰기 락, S=FK 검사 공유 락) |
| --- | --- |
| 포획 제출 | `bite_sessions`(X) → `catches` INSERT(users S) → `user_collection` upsert → `fish_records`(X) |
| 수확·먹이 | `aquarium_slots`(X, 칸 번호 순) → `users`(X) |
| 판매 (수정 전) | `catches`(X) → `users`(X) |
| 배치·빼기 | `aquarium_slots`·`catches`(X) → `users`(X) |
| 강화 | `users`(X) → `user_upgrade_stacks` → `upgrade_logs` |
| 구역 개방 | `users`(X) → `user_zones` INSERT |
| 릴·미끼 구매 | `users`(X) → `user_baits` |
| 던지기 | `users`(X) → `user_baits` → `bite_sessions` INSERT |
| 칸 확장 | `users`(X) |

판매만 `catches` → `users` 순서였다. 나머지는 `users`를 먼저 잡거나, 포획 제출처럼 `users`의 S 락을 쥐고 있었다.

### 재현

표는 읽어서 만든 것이라 맞는지 모른다. 그래서 `LockOrderConcurrencyTest`를 만들었다. 한 계정에 포획 3, 판매 2, 수확, 먹이, 빼기, 강화, 구역 개방, 릴, 미끼, 칸 확장, 던지기를 동시에 보내고, 다른 계정의 포획도 같이 돌린다. 이를 15라운드 반복한다.

수정 전에는 3회 모두 **락 실패 9건**이었다(판매 6~8건, 구역 개방·미끼 구매·칸 확장 각 0~1건).

### 해결과 결과

`AquariumService.sell`이 시작할 때 `lockForUpdate(userId)`로 `users`를 먼저 잠그게 했다(던지기·구매와 같은 방식). 수정 후 5회 모두 락 실패 **0건**이다.

한 가지 주의할 점이 있다. 이 결과가 보장하는 범위는 테스트가 돌린 흐름의 조합까지다. 표가 맞아 보인다고 "역순이 없다"고 말할 수는 없고, 새 흐름이 생기면 표와 테스트에 추가해야 한다.

## 배운 점

- 데드락은 InnoDB의 정상 동작이다. 버그는 대개 **그 예외를 어떻게 처리하느냐**, 그리고 **락을 어떤 순서로 잡느냐**에 있다.
- "가끔 실패"는 반복해서 재현해야 고쳤는지 알 수 있다. 라운드 반복과 동시 출발(`CountDownLatch`)이 가장 쓸모 있었다.
- 재시도는 최후의 수단이다. 락 순서를 맞추면 데드락이 사라져서 재시도가 필요 없다. 재시도를 쓴 곳은 순서를 바꿀 수 없던 유니크 INSERT(가입)뿐이다.
- 락 순서는 코드에서 흩어져 보이지 않으니, 표로 한 번 모아 보면 거꾸로 가는 흐름이 보인다. 그리고 그 표를 믿기 전에 테스트로 확인해야 한다.
- 락 실패가 500으로 새지 않도록 공통 핸들러(409)를 두는 것은 안전망으로 값이 싸다.
